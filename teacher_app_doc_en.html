ЄPython — Teacher's Guide

A step-by-step guide to creating tasks for exam mode (?mode=exam) with teacher_app.html. The most detailed part covers Tkinter tasks (section 4). Names of buttons and tabs below match the English interface of the app (add ?lang=en to its address to force English).

1. How it works

  1. You prepare a reference program and the check conditions in teacher_app.html and save them to a file name.task.json.
  2. The student opens ЄPython via a link like …/index.html?mode=exam&task=<URL of the JSON>.
  3. The Task button shows the assignment, Test runs the check, Submit produces a summary with a QR code.
  4. During a check, both your reference program and the student's program are run right in the student's browser (via Skulpt) with identical input and an identical action scenario. The results are then compared.
Key idea: the check does not ask "does the code look similar", it asks "does the program behave like the reference". Variable names, widget names, creation order and coding style can all differ. Only the observable result matters.
Language of the check report. The student's report (differences, scores, error messages) is generated by checker.js and is currently shown in Ukrainian regardless of the interface language. Section 4.10 and the table in section 13 give English translations of the common phrases.

2. Quick start: from reference to student link

1Write the reference and try it in ЄPython itself. Run it with the Run button. If the reference does not work in ЄPython, the check will not work either. This matters most for Tkinter: use only features that ЄPython supports.

2Open teacher_app.html and click 📂 Reference, then choose a .py file (or paste the code into the left editor).

3Click 🔍 Analyze. The app reports what it found: Tkinter, input(), print(), widget texts, top-level functions, and suggests a mode.

4Fill in "Task information": Title, Description (the text the student sees after pressing Task: put in everything they must know, especially the exact texts of buttons and labels and the input/output format), and Timeout in seconds (default 20).

5Choose the "Check mode" (section 3): Auto, Console, GUI (Tkinter), Console + Tkinter or Functions.

6Create tests for the chosen mode in the right-hand panel (tabs "Tkinter: actions", "Console: tests", "Functions").

7Add "Requirements" if needed (for example require def solve, forbid call eval) and "Additional files".

8Adjust "What to check (options)" (section 8). The defaults suit most tasks.

9Click ▶ Trial run. ЄPython opens in exam mode with your task (it is passed through localStorage, address ?mode=exam&task=test). Paste the reference code into the editor and press Test: the report must say "all matches the sample", 100 %. If not, the task is configured incorrectly.

10Try "student" variants:

  • a correct program with different variable and widget names: it must pass;
  • a program with a typical mistake (different button text, handler not working, etc.): it must show differences;
  • an empty program and a program with a syntax error: make sure the report is understandable.

11Save the task: 💾 Save JSON produces name.task.json. You can reopen and edit it later with 📥 Open.

12Publish the file and give the students the link (section 11).

Tip. After every change, repeat step 9: running the reference against itself is the fastest way to catch a mistake in the scenario.

4. Tkinter tasks (in detail)

4.1. How the GUI check works

  1. The reference program is run. Instead of the real mainloop() the checker inserts its own "session".
  2. A snapshot "Initial state" is taken: the full widget tree of the window with each widget's class, text, state, value and children.
  3. The scenario actions are executed one by one (click a button, type text…). A new snapshot is taken after each action.
  4. The same steps are repeated for the student's program.
  5. The snapshots are compared step by step. Each step is a separate "test" in the score.
In other words, you write a user scenario, and the system checks that the student's program reacts at every step just as yours does.

4.3. How a widget is found for an action

The student's variable names are unknown, so widgets are found by visible text and type, not by name:

  • click Text looks for a widget whose text equals Text: first an exact match, then case-insensitive and ignoring surrounding spaces. Buttons and other widgets with an invoke method have priority.
  • type, append, key look for input fields (Entry, ttk.Entry, Spinbox, Text).
  • select works on a Listbox; combo on a ttk.Combobox; scale on a Scale / ttk.Scale.

If there are several matches, use an ordinal number in square brackets: click[2] + is the second button labeled "+". Numbering goes top to bottom, left to right by position on screen. The default number is 1.

The main rule that follows: the student must follow exactly the captions of the widgets the scenario refers to. If the scenario says click Next but the student's button says "Continue", the action cannot be performed, and this is reported as an error. So list in the task description all the texts that must appear in the interface.

4.4. Scenario commands

Write one command per line in the "Tkinter: actions" tab. Lines that start with # are comments. A comment after a command on the same line is not supported (it would become part of the command text): put it on its own line.

4.5. How to build a scenario

  1. Follow the user's path: enter data → press a button → (if needed) check the consequence with the next action.
  2. Cover different branches of the program. One scenario is one "walkthrough". If the program has, say, division by zero or an empty field with an error message, add the corresponding steps at the end of the same scenario; a task has only one scenario.
  3. Every action is a separate step in the score (plus "Initial state"). The finer the steps, the more accurate the score and diagnostics: the student sees at which step the difference appeared.
  4. Do not make very long scenarios (more than 15–20 steps), the result becomes hard to read.
  5. You do not need a separate "verifying" action. The next snapshot already shows the result in a Label. If the result appears in a messagebox, it is captured in the same step.

4.6. Dialog windows

Real message boxes are not shown during the check. Instead the system records which dialog was called and with what text, and automatically "answers":

CallAutomatic answer
showinfo, showwarning, showerror"ok"
askyesno, askokcancel, askretrycancel, askyesnocancelTrue
askquestion"yes"
askstring, askinteger, askfloatNone (the user "cancelled")
askopenfilename, asksaveasfilename, askdirectory…empty string / None (no file chosen)
So do not build tasks around askstring / askinteger and file dialogs: the answer is always "cancelled" and handling of a typed value cannot be checked. Use a regular Entry field and a button instead.

The kind of dialog and the message text are compared (whitespace and case according to the text options). The dialog title is not compared. You can turn dialog comparison off with the "dialogs" option.

4.7. Things worth knowing

  • mainloop(). The student's program may call root.mainloop() or tk.mainloop(). If there is no such call, the checker tries to find the window itself: via a root variable, or by calling a function named create_app / main / run / start / setup, etc. If there is no window the report says "tkinter window not found".
  • Variable names. The student may name variables anything, including tk = Tk() or root = Tk(). The checker does not depend on it.
  • Blocking calls. wait_window, wait_variable, wait_visibility do not block; the window is simply refreshed. grab_set is safe.
  • Toplevel windows. The snapshot is built from the main window; extra windows created from it are recorded as its children. If a second window must be checked, make sure in the trial run that it appears in the report.
  • Randomness and time. If the program uses random, the seed value (default 12345) is fixed for both reference and student, so results match. Programs that depend on the current time (time.time(), datetime.now()) or on after() timers cannot be checked reliably: avoid them in tasks.
  • Errors in the reference. If an action fails already in the reference, it appears in the report as a warning "[зразок] крок …" ("[sample] step …"). The student sees it too, so fix the scenario before publishing.
  • Closing the window. If the program closes the window at some point (root.destroy()), the snapshot shows "closed". A mismatch (closed in one, open in the other) is a difference.

4.8. What Tkinter checking cannot do

  • It does not emulate the mouse by coordinates: clicks on a Canvas, dragging, double-click, right-click.
  • It does not compare appearance pixel by pixel: colors, fonts and layout are compared only through the "style" and "layout" options, at the level of parameters.
  • It does not check canvas drawings by coordinates/colors, only item types and texts.
  • Keys are sent only to input fields.
  • You cannot click a widget that has no text (an image button). Use buttons with text in your tasks.
  • Timers and animations (after) are not reliable for checking.

4.9. Sample tasks

Example 1. Counter (button + label)

Student assignment: "Create a window titled Counter with a label showing 0 and a button labeled Next. Each press of the button increases the number by 1."

Reference:

import tkinter as tk

root = tk.Tk()
root.title('Counter')
lbl = tk.Label(root, text='0')
lbl.pack()

def inc():
    lbl.config(text=str(int(lbl.cget('text')) + 1))

btn = tk.Button(root, text='Next', command=inc)
btn.pack()
root.mainloop()

click Next
click Next
click Next

Steps: "Initial state" + 3 actions = 4, plus 1 for the requirements (if any are set). The score is calculated from these steps.

4.10. What the Tkinter report looks like

The report shows, step by step, where the difference is: the path to the widget (Tk › Label «1»), what was compared (text, state, value…) and the reference and student values. This is an actual report (in Ukrainian) for a student who named the button "Back" instead of "Next":

Рівень: 1 з 4 (25%)

In English: "Differences: 3 · Score: 1 of 4 (25%) · Initial state: text (sample="Next", student="Back") · Step 1: the action could not be executed in the student's program: widget with text 'Next' not found (#1) · text (sample="1", student="0") · (+1 earlier differences are not repeated)". A difference that persists is not repeated at every following step; it is only noted as "still present".

5. Console tasks

Each test is a set of lines that the "user" types in response to consecutive input() calls.

=== Test 1
3
5
=== Test 2 [x2]
10
20
  • === Name starts a test. The suffix [x2] at the end of the name is the test's weight.
  • Each following line is the answer to one input().
  • Blank lines and lines starting with # are ignored. An empty input is written <empty> (the Ukrainian <порожньо> works too). A line that itself starts with #, < or = needs a \ in front (\#text).

The ⚡ Generate from reference button runs the reference and chooses input data from the input() prompts. Review and edit the result: the generator does not always guess sensible numbers.

Count input() calls exactly. If a test has fewer lines than the reference reads, the report shows "⚠ Тести неповні" ("Tests incomplete"): the result of such a test is unreliable. Give as many lines as there are input() calls actually executed.

The output text is compared (by default ignoring extra spaces and blank lines; numbers with tolerance 1e-6), as well as the exception type and the exit code.

6. Function tasks

A mode for modules of functions. One expression per line:

sum_list([1, 2, 3])
is_prime(7)
[x3] mean([1, 2, 4])
a = [3, 1, 2]; sort_list(a); a

The third line has weight 3 ([x3] at the start). The fourth has several statements separated by ;; the last expression is the result.

  • First the whole student code is executed as a module (input() is not available), then each expression is evaluated.
  • The repr() of the result is compared. Numbers are compared with tolerance; True and 1 are different (also inside lists).
  • If the reference raises an exception, the student must raise an exception of the same type.
  • Module state is kept between calls (global variables change), exactly as in the reference.
  • The time limit of a single call is "call timeout" (3 s by default).

🧩 Template from reference lists the functions found as comments; substitute real arguments.

7. Code requirements

The code structure is checked without running it. English or Ukrainian keywords are accepted. The explanations after "—" below are for reference only; do not type them in:

require def solve        — a function with this name
require def              — at least one function
require class Animal     — a class
require for / while / if / try / with / lambda / global
require comprehension    — a list/dict/set comprehension or generator
require recursion        — any recursive function (or: recursion fact)
forbid call eval         — forbidden call
forbid import numpy      — forbidden import
forbid for               — e.g. "solve without loops"

All requirements together are one step in the score. Text after # is a comment.

Useful when a "result" can be obtained by a shortcut: forbid call eval for a calculator, require recursion for a recursion task, forbid import math for a "no libraries" task.

9. How the score is calculated

  • The result is "score X of Y (Z%)": the sum of weights of passed steps divided by the sum of weights of all steps.
  • A step is passed if it has no differences at all.
  • Steps: for console, each test (weight from [xN]); for functions, each call (weight from [xN]); for GUI, "Initial state" and each action (weight 1); code requirements are one step.
  • If the student's program does not run at all, the score is 0 with the full number of steps in the denominator.
  • The Test button can be pressed any number of times. Submit uses the last check, the number of checks and the time.

Example. A console task with 4 tests (weights 1, 2, 1, 1) and the requirement forbid call eval. Total 1+2+1+1+1 = 6. A student passes everything except the weight-2 test → 4 of 6 (67%).

12. What the student sees

  1. Opens the link. Three buttons appear at the top of the screen.
  2. Task shows a window with the title and description and a start button. After pressing it, timing and counting of keystrokes and clipboard pastes begin. Reopening the assignment does not reset the counters.
  3. The student writes the program in the editor and runs it as usual.
  4. Test checks the code in the editor and shows the report in a separate window. It can be repeated without limit.
  5. Submit shows a window with the time, counters, the result of the last check, the IP address and a QR code. The student saves the image and gives it to you. You read it with the "🗃️ Check result" button in teacher_app.
The student's report shows the reference values (for example зразок="42", i.e. sample="42"). Write the assignment so that this is not a problem, and for final checks use console-test values that do not appear in the examples of the assignment.

14. Limitations and security

  • The reference code is stored in the task file and is downloaded into the student's browser, so technically it is accessible through developer tools. Do not put anything secret in the reference. For tests where this is critical, set conditions that demand a specific appearance, not just an answer.
  • The check runs in the student's browser. The result (score, QR code) is produced on the student's computer; the QR encryption key sits in the public page code, so the QR is not a guarantee against forgery. For high-stakes grading, cross-check it with other signs (time, pastes, IP) and, if possible, re-run the program on your own computer.
  • The student's program is run without isolation: an infinite loop is stopped by the timeout, but very heavy programs (for example enormous lists) can freeze the tab.
  • The IP address is obtained from external services and may be unavailable offline.
